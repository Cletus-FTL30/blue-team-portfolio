# ADS-001 - AWS Credentials Honeytoken Access

*Alerting & Detection Strategy (ADS). Detection engineering artifact documenting the goal,
logic, blind spots, false-positive handling, validation, and response for a single detection.*

| | |
|---|---|
| **Detection ID** | ADS-001 |
| **Wazuh Rule IDs** | 100300 (alert, level 12), 100301 (suppression, level 0) |
| **Status** | Production - validated against live attack |
| **Author** | Cletus |
| **Data Source** | Linux auditd (SYSCALL/PATH records) via Wazuh agent |
| **Platform** | Linux (Ubuntu 24.04) |

---

## 1. Goal

Detect any access to a planted AWS credentials honeytoken. Because the file is a decoy
with **zero legitimate use**, any read is - by construction - either an intruder performing
credential theft or a tool sweeping the host for secrets. The detection provides a
high-fidelity, near-zero-false-positive signal of credential-access activity on the host.

## 2. Categorization (MITRE ATT&CK)

| Field | Value |
|-------|-------|
| **Tactic** | Credential Access (TA0006) |
| **Technique** | T1552.001 - Unsecured Credentials: Credentials In Files |
| **Related (attack chain observed)** | T1059 Command & Scripting Interpreter (reverse shell), T1083 File & Directory Discovery (credential sweep) |

## 3. Strategy Abstract

A realistic-but-fake AWS credentials file is planted at a standard, attacker-expected
location (`~/.aws/credentials`). A Linux `auditd` watch rule tags every access to that
exact path with the key `honeytoken_aws`. The Wazuh agent forwards audit events to the
manager, where a custom rule (100300) raises a level-12 alert on any tagged access. A
companion suppression rule (100301) discards reads generated by Wazuh's own file-integrity
scanner so the system does not alert on itself.

## 4. Technical Context

**The bait.** `/home/cletus1/.aws/credentials`, `chmod 600`, containing realistic
`AKIA`-format access keys across two profiles (`default`, `prod-backup`). The realism is
deliberate: an attacker or automated tool must be unable to distinguish it from a genuine
credentials file, or the deception fails.

**The audit watch (persistent).**
```
-w /home/cletus1/.aws/credentials -p rwxa -k honeytoken_aws
```
Stored in `/etc/audit/rules.d/honeytoken.rules` so it survives reboots. `-p rwxa` captures
read, write, execute, and attribute changes; **read (`r`) is the critical permission** -
credential theft is a *read*, which File Integrity Monitoring alone cannot detect (FIM
only sees modification).

**The alert rule (100300).** Chained as a child of Wazuh's base audit rule via
`<if_sid>80700</if_sid>` (a sibling relationship using `<decoded_as>` fails to evaluate,
as the base rule matches first). Matches `audit.key = honeytoken_aws`. Level 12.

**The suppression rule (100301).** Wazuh's `wazuh-syscheckd` reads the file during FIM
scans. Rule 100301 matches the decoded exe path `/var/ossec/bin/wazuh$` (the decoder
truncates `wazuh-syscheckd` at the hyphen - matched against the decoded value, not the raw
one) and sets level 0 to suppress these self-generated reads.

## 5. Blind Spots & Assumptions

*What this detection cannot see, stated honestly:*

- **Offline/raw-disk reads.** An attacker reading the file via a mechanism that bypasses
  the audited syscall path (e.g. reading the raw block device, or from a mounted disk
  image offline) would not generate an audited access. auditd observes syscalls on the
  running system, not out-of-band access.
- **auditd tampering.** A sufficiently privileged attacker who disables or unloads the
  audit rule (or stops `auditd`) before reading the file defeats the detection. Mitigated
  partially by also auditing changes to audit config, but a root-level attacker who
  neutralises auditd first is a gap.
- **Agent/manager availability.** If the Wazuh agent is stopped or the network path to the
  manager is down at the moment of access, the local audit event exists but no alert is
  raised until (or unless) it is forwarded. Assumes the pipeline validated in Phase 1 is
  healthy.
- **Attacker recognises the decoy.** A careful attacker who inspects the keys, notices they
  are non-functional (fail against AWS), and avoids further interaction limits follow-on
  signal. The *initial* read is still detected; downstream use is not guaranteed.
- **Assumes the host runs no legitimate AWS workload.** Correct for this lab. On a real host
  that *does* use AWS, this exact file could not be the honeytoken - a decoy profile or
  alternate path would be required.

## 6. False Positives

| Source | Likelihood | Handling |
|--------|-----------|----------|
| Wazuh `wazuh-syscheckd` FIM scan reads the file | Certain (recurring) | **Suppressed** by rule 100301 (level 0). Validated. |
| Backup software / AV / indexing tools reading the home dir | Possible on real hosts | Would need a tuned exclusion per tool (same pattern as 100301). None present in this lab. |
| The owner legitimately opening the file | None by design | The file has no legitimate purpose; the user is instructed never to touch it. |

Net effect: with the syscheckd suppression in place, **no false positives were observed**
across validation. The design goal - false positives eliminated structurally, not tuned
away - holds.

## 7. Validation

Validated **two independent ways**:

1. **Unit test (`wazuh-logtest`).** A `cat` read decodes and matches rule 100300 (level 12,
   "Alert to be generated"). A `wazuh-syscheckd` read matches rule 100301 (level 0,
   suppressed). Deterministic and repeatable.
2. **Live attack (end-to-end).** From the Kali attacker: reverse shell -> host discovery ->
   automated credential sweep (`grep -rniel "aws_access_key\|secret\|password\|api_key"`).
   The sweep read the honeytoken as a side effect of ordinary looting, and rule 100300
   fired with `data.audit.command: grep` - confirming detection of a realistic attack, not
   just a manual read.

## 8. Priority & Response

**Priority: High (level 12).** A honeytoken read is treated as a confirmed intrusion
indicator, not a suspicion.

**Analyst response playbook:**
1. Treat the source host as compromised until proven otherwise.
2. From the alert, capture: `data.audit.command`, `data.audit.exe`, `data.audit.auid`
   (original login user), `data.audit.tty`, `data.audit.pid`, and timestamp.
3. Pivot on `auid` and session ID to reconstruct the surrounding activity (what ran before
   and after the read) - the read is one point in an intrusion, not the whole story.
4. Check for the initial-access vector (new sessions, reverse-shell connections, unexpected
   parent processes) and for follow-on actions (exfiltration, lateral movement, persistence).
5. Contain: isolate the host, rotate any *real* credentials that share the environment,
   preserve the audit log for forensics.
